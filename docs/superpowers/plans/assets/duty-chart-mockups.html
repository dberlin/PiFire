The finding that reframes the request

The history chart can't show duty because history doesn't record duty.

Duty is computed, published and rendered live — the dashboard has AUGER DUTY and FAN DUTY tiles today. But nothing writes it to the history store, and the one slot in the schema that looks purpose-built for it records hardcoded zeros. So this is a persistence change with a charting tail, not the other way round. Roughly 70% of the work sits behind the API.

1 · The visual treatment

Temperature is °F on the left axis; duty is a 0–100 % control signal. They can't share a scale — a 225 °F trace and a 0–1 ratio on one axis pins duty flat to the floor. Three ways out, all rendered below against the same synthetic four-hour brisket cook: a startup ramp, a settle, a long hold, and a stall.

A · Right-hand percent axis

Chosen 0 px of extra height

Duty gets its own scale, fixed to [0, 100] so a line's height means the same thing in every window and every cook — and a stepped path, because duty is a step function and interpolating it draws ramps that never happened. Shared gridlines are what make “the auger ramped forty seconds before the temperature moved” readable at a glance. Turn on Auger requested to see the duty floor clamping — the line the controller asked for, separating from the one it got. It records by default and draws off by default; the chips are how you reach it.

B · Stacked duty panel

Held as the escalation ~110 px of height

The classic volume-panel arrangement: shared x-axis, synced cursor, total separation of units. It is unambiguously the clearest reading of duty on its own — and it costs about 110 px of vertical budget on a page that is already overflowing a 1280×720 viewport. PiFire runs on kitchen and garage tablets, so that is real money. Escalate to this only if A tests badly with four or more probes already on the plot.

C · Filled band inside the temperature axis

Rejected

Cheapest to build and it does fit — but a duty line's vertical position now means nothing, since it is scaled into whatever the bottom fifth of the temperature range happens to be. The band moves when a probe goes cold. Reading a value off it requires knowing a conversion nobody is holding in their head.

2 · The toggle

The question you actually asked

All three work. They differ on discoverability, on touch, and on whether they can do anything beyond duty.

1 · uPlot's own legend

Free

Already rendered and already clickable — zero code. But nothing signals that it is a control, and a 12 px text target fails on the touchscreen this runs on.

3 · One “Show duty” switch

Simplest

One decision, unmissable. But auger and fan arrive together whether you wanted both or not, and it does nothing for the probes.

2 · Chip row above the chart

Chosen Closes an existing hole

36 px touch targets, visible as controls, and each series independent. The reason to prefer it, though, is what it fixes on the way past: today a probe you disabled in Settings has its history silently discarded — the adapter drops hidden datasets outright because, in its own words, “the chart has no per-series visibility toggle to defer the decision to”. A chip row lets hidden mean off by default but available instead of invisible. Try Ambient (off) above.

Hard constraint · whichever wins

HistoryChart.tsx rebuilds uPlot whenever the series shape changes, and that shape is keyed on label + colour. Implementing a toggle by adding or removing entries in the series array therefore drops the user's zoom on every click. Toggles must go through setSeries(i, {show}) on the live instance, with visibility held outside the shape key — every series always constructed, only show changing. Worth its own test: this looks perfect in a screenshot and is infuriating in the hand.

3 · The trap in the downsampler

Would ship silently

prepare_chartdata thins points by shape fidelity, picking one shared index set for every series against a tolerance measured in degrees — 2.0 °F by default. A cycle ratio lives in 0.0–1.0, so a full 0 → 100 % auger swing moves one unit: half the tolerance. Duty contributes nothing to which points survive, and short pulses between two thermally quiet samples vanish.

Below: the same twenty minutes of a steady hold, reduced both ways. Faint ticks mark the samples the reducer kept.

As it would ship

Pulses lost

Indices chosen by temperature shape alone. The duty trace is drawn through whatever survived — every pulse between kept samples is gone, and the line reads as a slow drift that never happened.

Duty joins the fidelity check

Correct

Feed cycle_ratio × 100 into the check so a 2 % duty change carries the same weight as 2 °F. Every edge survives, at a cost of a few dozen extra points.

The code already makes this exact argument for the target and setpoint series — “step functions just like P/F … they must share the same fidelity check or a step edge can be smoothed into a ramp that never happened.” Duty is the same class of series; it just needs the unit correction too. Prove it with a negative control: a one-sample pulse on a flat trace must survive reduction with the correction and must not survive without it. Assert both directions, or the test proves nothing.

4 · Where duty gets stored

ApproachCostVerdict
B1 Fill the existing ext_data CR/RCR stub for real Low Ships behind a setting that defaults off, so most users get a duty chart with no duty on it. Inherits a bug where unpack_history takes its key set from row 0 — enable it mid-cook and every later row is silently dropped.
B2 Real cycle_ratio / fan_duty columns + migration Medium Recommended. ~12 bytes/row, under 350 KB across full retention. Direct precedent: _migrate_history_to_numeric_psp already rebuilds this table. Pre-migration rows read NULL, which the adapter already null-pads into gaps.
B3 Don't persist — overlay the live socket tail only Trivial The point of the history page is looking back. Vanishes on reload, never reaches cook files.

Two things ride along with B2. Retire the CR/RCR stub in the same change — once duty has real columns, leaving a second duty path that reports zeros is just a lie with a longer lifespan. And extract the duty computation into one helper called by both the status write and the history write: it already carries a Manual-mode branch, a PWM branch and fan-off gating, and two copies would drift on exactly the cases nobody checks. A dashboard reading 0 % while history plots 100 % for the same instant is a bug no one would think to look for. It is a cross-process seam, so pin both ends.

Decided

All four · 2026-08-25
1
Overlay on a right-hand axis, not a stacked panel.
Costs no vertical space on a page already overflowing 720p, and shared gridlines are what make the correlation readable. B stays held as the escalation if the overlay reads badly once four or more probes are on the plot.
2
Chip row for visibility.
Touch-sized, obviously a control, and it recovers the disabled-probe history the chart currently throws away. Now on the critical path — the chips are the only way to reach the duty series, so this ships with the chart rather than trailing it.
3
Cook files get duty too.
Same code path; costs a format bump, and cooks saved before the change render duty as gaps. “The live chart has it but my saved cook doesn't” is the worse outcome.
4
Requested duty is recorded alongside applied.
The duty floor sets the lowest temperature a grill can actually hold, and the shipped 25 s default can't hold 225 °F on a real MAK. Right now that failure is invisible: the grill just runs warm. Plot both lines and it is obvious — the controller asks for 8 %, the floor clamps to 12 %, and they visibly separate and stay separated. This is what RCR in the dead stub was supposed to be.
5
Storage: real columns (B2), decided by consequence.
Not asked directly, but settled by (4). The reason to record requested duty is to make the duty-floor failure visible — and a feature gated on a setting that defaults off cannot make anything visible. B1 is incompatible with the decision above rather than merely worse than it. Flagged in case avoiding schema churn matters more than (4) does.

Three duty columns, then — applied auger, requested auger, fan — so the migration is written once rather than revisited. Phasing, the contract and codegen notes, the mobile SVG chart's second-axis problem, and the parallelisation split are in the design doc alongside this page.
